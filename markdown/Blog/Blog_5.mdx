A well-designed **REST API** does more than expose resources—it **reduces coordination cost** between backend and client teams. When contracts are inconsistent, every web and mobile client reimplements ad-hoc error parsing, retry logic, and pagination edge cases. This article covers patterns that keep **web apps**, **mobile apps**, and future integrations on stable footing.

## Resource modeling and predictable URLs

Good APIs feel **boring**: nouns name resources, HTTP verbs map to safe operations, and URLs do not encode every filter as a different path shape.

Principles:

- **Stable identifiers**: opaque IDs (UUIDs or snowflakes) beat auto-increment leaks across tenants.
- **Consistent nesting**: `/projects/{id}/tasks` reads clearly; avoid deep trees that mirror your database join depth one-to-one unless clients need that shape.
- **Filtering and sorting** as query parameters with documented allowed fields.

Document **examples** for every non-trivial endpoint—OpenAPI (Swagger) helps, but narrative matters too.

## Pagination — offset vs cursor

**Offset/limit** pagination is easy to implement but performs poorly on large datasets (deep pages get expensive) and behaves badly if rows shift between requests.

**Cursor-based** pagination returns a **next cursor** tied to a stable sort. Clients pass the cursor to fetch the next page. It scales better and avoids “skipped/duplicate rows” when data changes mid-pagination.

Whichever you choose, document:

- **Sort order** (always explicit),
- **Maximum page size**,
- **Empty result** behavior.

## Errors clients can actually handle

Return **structured JSON** for errors, not HTML stack traces:

- Use **correct HTTP status codes** (4xx client, 5xx server).
- Include a **machine-readable code** (`PAYMENT_DECLINED`, `RATE_LIMITED`) and a **human message**.
- Optionally add **field-level** errors for validation (`422` with per-field map).

Mobile apps especially benefit from **stable codes**—they map to localized strings without scraping English sentences.

Example shape (illustrative):

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "One or more fields are invalid.",
    "details": { "email": "INVALID_FORMAT" }
  }
}
```

## Idempotency for dangerous or retry-prone operations

Users double-tap. Networks retry. **Idempotency keys** let servers recognize duplicate submissions:

- Client sends `Idempotency-Key` header (or body field) on **POST** operations that create money, orders, or irreversible state.
- Server stores the key with the **result** for a TTL; replays return the same response.

This pattern is essential for **payments**, **signup flows**, and **device pairing**—anywhere retries are likely.

## Versioning and compatibility

Prefer **additive** changes: new optional fields, new endpoints. When you must break behavior:

- **URL versioning** (`/v1/`, `/v2/`) is explicit and cache-friendly.
- Communicate **sunset** dates and maintain overlap when possible.

Avoid silent changes to **field meaning**—clients cache assumptions.

## Caching semantics

Use **ETag** and **Last-Modified** for **GET** resources that change infrequently. Clients send `If-None-Match` and receive `304 Not Modified`—saving bandwidth on mobile networks.

Set **Cache-Control** intentionally for public vs private data; never mark personalized responses as publicly cacheable.

## Security basics (non-negotiable)

- **HTTPS** everywhere; **HSTS** at the edge for browser clients.
- **Authentication**: Bearer tokens with short lifetimes; refresh flows documented clearly.
- **Authorization** checked server-side on every request—never trust client-only checks.
- **Rate limiting** with clear **429** responses.

## Closing

Simple, consistent APIs age well. Invest in **error models**, **pagination**, and **idempotency** early—your web and mobile teams will ship faster with fewer “API surprise” bugs.
